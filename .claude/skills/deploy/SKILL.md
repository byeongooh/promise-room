# 배포

Vercel이 `main` 브랜치 푸시를 감지해 자동 배포한다. 따로 배포 명령은 없다.
그래서 **푸시 = 배포**이고, 푸시 전에 반드시 검사한다.

## 순서

### 1. 검사 — 건너뛰지 않는다

```bash
npx tsc --noEmit
npm run build
```

빌드가 통과하지 않으면 푸시하지 않는다. Vercel에서 실패하면 프로덕션이
이전 배포에 머무르고, 사용자는 왜 안 바뀌었는지 알 수 없다.

대중교통·길찾기 쪽을 건드렸다면 실제 호출까지 확인한다:

```bash
node --env-file=.env.local scripts/check-odsay.mjs
```

네 경로(성수→강남 / 안양→롯데월드 / 서울→부산 / 서울→대전)가 모두 `✓`여야 한다.

### 2. 올릴 것만 고른다

```bash
git status --short
```

`.env.local`이나 `.migration-backup/`이 목록에 보이면 **멈추고 알린다.**
`.gitignore`가 뚫린 것이므로 그것부터 고쳐야 한다. 둘 다 비밀 값이 들어 있다.

`git add -A`로 뭉뚱그리지 말고 이번에 고친 파일을 이름으로 지정한다.

### 3. 커밋 — 왜 그렇게 했는지를 적는다

무엇을 바꿨는지는 diff에 있다. 커밋 메시지에는 **왜**를 적는다.
이 저장소의 로그가 사실상 설계 기록이다.

- 한국어로 쓴다.
- 첫 줄은 무엇을 했는지 한 줄.
- 본문에 **어떤 문제가 있었고, 왜 이 방법을 골랐는지**를 적는다.
- 다른 방법을 버렸다면 왜 버렸는지도 적는다. 나중에 같은 고민을 반복하지 않는다.
- 실제로 확인한 결과가 있으면 숫자를 남긴다.

PowerShell에서 여러 줄 메시지를 넘길 때는 heredoc을 쓴다.
PowerShell here-string(`@'...'@`)을 Bash 도구에서 쓰면 `@`가 그대로 들어간다.

```bash
git commit -F- <<'EOF'
가까운 거리에 도시 간 경로가 섞여 엉뚱한 시간이 나오던 것 수정

안양에서 잠실까지 "기차 11분"이 떴다. 실제로는 62분이다.
(원인과 고른 방법, 버린 방법)

확인: 안양→롯데월드 버스 62분 · 지하철 63분

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
```

### 4. 푸시

```bash
git push origin main
```

### 5. 배포 확인 — 여기까지가 배포다

Vercel MCP로 최신 배포의 커밋 해시와 상태를 확인한다.

```
list_deployments(projectId: "promise-room", teamId: "team_BAGhiQBEzlY5sWWV5h50mpOz")
```

방금 푸시한 커밋이 `state: "READY"`인지 본다. 아직이면 1~2분 뒤 다시 본다.
푸시만 하고 "배포했습니다"라고 말하지 않는다.

## 환경변수를 새로 넣었을 때

**저장만으로는 적용되지 않는다.** 기존 배포본은 만들어질 때의 환경변수를
그대로 들고 있다. 사용자에게 Vercel → Deployments → 맨 위 `⋯` → **Redeploy**를
안내하고, 재배포가 실제로 생겼는지 `list_deployments`로 확인한다.

## 말할 때

- 확인한 것과 확인하지 못한 것을 나눠서 말한다. 카카오 로그인이 필요한 화면은
  직접 볼 수 없으므로 "빌드는 통과했지만 화면은 확인 못 했다"고 밝힌다.
- 사용자는 웹 개발이 처음이다. 용어를 쓰면 한 줄로 풀어 준다.
